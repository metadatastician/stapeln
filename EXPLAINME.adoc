The README makes claims. This file backs them up with evidence from real code.

== Core Claims & Evidence

=== Claim 1: "ReScript-TEA: All State Transitions Are Pure Functions"

**From README** (lines 180-192):
____
All state transitions are **pure functions**:

```rescript
type model = { /* app state */ }
type msg = AddComponent | DragMove | Deploy | Simulate | ...
let update: (model, msg) => (model, effect<msg>)
let view: model => React.element
```

Time-travel debugging. Fully testable. Predictable.
____

**Evidence**: `/var/mnt/eclipse/repos/fleet-ecosystem/stapeln/frontend/src/App.res` implements the TEA pattern: immutable `type model`, pure `update` function, deterministic `view` function. Paragon, Cisco, LagoGrey, and Settings views at `/var/mnt/eclipse/repos/fleet-ecosystem/stapeln/frontend/src/views/` all follow this pattern.

**Caveat**: TEA pattern ensures *local* UI determinism. Backend state (VeriSimDB, Elixir GenServers) may have race conditions not visible in ReScript code. `effect<msg>` side effects (HTTP calls) can fail unpredictably.

=== Claim 2: "miniKanren Security Engine: Deterministic Logic Programming"

**From README** (lines 196-220):
____
**Why miniKanren, not an SLM?**
* ✅ Deterministic (same input → same output)
* ✅ Explainable (full provenance chain)
* ✅ Instantly updateable (new CVEs added immediately)
* ✅ No hallucinations (can't invent fake CVEs)
* ✅ Fast (milliseconds, not seconds)
* ✅ Small (< 10 MB, no GPU needed)
____

**Evidence**: `/var/mnt/eclipse/repos/fleet-ecosystem/stapeln/security-rules/` contains Scheme files with miniKanren rule definitions. Example: `/var/mnt/eclipse/repos/fleet-ecosystem/stapeln/security-rules/rules/expose-ssh-rule.scm` defines the constraint that SSH port 22 must never expose to public interface.

**Caveat**: Rules are only as good as their *specification*. A CVE written incorrectly into miniKanren will be deterministically wrong. No formal verification that the rule set covers actual attack surface.

=== Claim 3: "VeriSimDB Multi-Modal Storage: 6 Modalities"

**From README** (lines 237-260):
____
```elixir
# Store stack with multiple modalities
VeriSim.insert(%{
  uuid: "stack-abc123",
  modalities: [:graph, :semantic, :temporal],
  data: %{
    graph: {"stack:abc123", "stapeln:hasComponent", "comp:nginx"},
    semantic: "<http://example.org/stack/abc123> rdf:type stapeln:Stack",
    temporal: %{timestamp: DateTime.utc_now(), event: "created"}
  }
})

# Query with SPARQL
VeriSim.sparql_query("""
  SELECT ?component WHERE {
    ?stack stapeln:hasComponent ?component .
    ?component stapeln:exposesPort 22 .
  }
""")
```
____

**Evidence**: `/var/mnt/eclipse/repos/fleet-ecosystem/stapeln/backend/lib/verisimdb_integration.ex` integrates VeriSimDB graph, semantic (RDF), and temporal modalities. Stack data stored via `VeriSim.insert/1` with structured UUID and metadata at `/var/mnt/eclipse/repos/fleet-ecosystem/stapeln/backend/lib/components/stack.ex`.

**Caveat**: Multi-modal storage adds complexity. Query results depend on modality consistency—if graph says "nginx" but semantic says "apache", consensus is undefined.
